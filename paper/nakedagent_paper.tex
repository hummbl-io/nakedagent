\begin{abstract}
NakedAgent explores how much of a terminal coding agent can be implemented using Python's standard library. Its Python package declares no third-party runtime dependencies and provides four foundation tools, a fenced-text invocation grammar, two HTTP wire adapters, and a tool-substitution interface that also updates prompt examples. An optional functional execution path separates deterministic state transitions from model and tool effects. Its versioned JSONL verifier replays reported events without model inference or tool execution and detects inconsistencies against recorded hashes and final-state fields. This is a transcript-consistency mechanism: it neither authenticates a rewritten transcript nor proves that reported effects occurred. We specify the actual hash inputs, distinguish three execution paths and their budgets, and provide offline counterexamples that delimit these guarantees. A previously recorded three-instance SWE-bench Lite pilot supplies a failure-analysis case study, including invalid harness runs and a reported corrected run with zero resolved tasks. Its absent raw trajectories and uncontrolled sampling prevent comparative performance conclusions. The contribution is an inspectable architecture and a reproducibility contract, not a proof of secure or capable autonomous execution.
\end{abstract}

\section{Scope and contribution}
Coding agents combine model outputs with repository inspection, editing and command execution. SWE-agent studies how the agent--computer interface affects performance~\cite{yang2024sweagent}; SWE-bench provides issue-resolution tasks and test-based evaluation~\cite{jimenez2024swebench}. NakedAgent asks a narrower architectural question: can the interaction loop, tool dispatch, provider transport and optional replay layer be built without third-party \emph{Python runtime packages}?

The answer at the inspected source revision is constructive: these components exist using the standard library~\cite{nakedagentsource}. That fact does not establish competitive task success, lower defect rates, or lower total supply-chain risk. Python, the operating system, model server, model weights, command-line programs and optional plugins remain dependencies of a deployment. The package also uses a setuptools build backend; build-time requirements are outside the runtime count.

This revision contributes (1) a source-bound description of the architecture and its substitution seam; (2) a conditional replay argument with an explicit threat model and executable counterexamples; and (3) a separation of historical pilot observations from a prospective evaluation protocol. It does not claim invention of fenced tool calls, search/replace editing, functional reducers or hash chains.

\section{Architecture and effect boundaries}
\subsection{Dependency scope}
Let $D_P$ be the third-party Python packages required by the foundation runtime, excluding plugins and external services. The pinned \texttt{pyproject.toml} declares $D_P=\varnothing$. The companion script statically enumerates absolute imports in \texttt{nakedagent/*.py} and checks them against the executing interpreter's standard-library module inventory. This supports the package-level claim, not a complete software bill of materials or a guarantee about dynamically imported plugins.

The provider adapter in \texttt{llm.py} uses \texttt{urllib.request} for Ollama's \texttt{/api/chat} and an OpenAI-compatible chat endpoint. API keys are obtained from a named environment variable. The Ollama default is \texttt{http://localhost:11434}; HTTP over loopback is still network communication, and the configurable host can point elsewhere. Compatibility with every server advertising a similar API is not established. The source supports incremental response parsing through the \texttt{stream} argument, so absence of a rich terminal framework is not absence of streaming transport.

\subsection{Four foundation tools}
The registry exposes functions with the interface
\[
 t:(\text{args},\text{content},\text{workspace})\longrightarrow\text{result string}.
\]
This signature standardizes dispatch; it does not make filesystem or subprocess effects pure or deterministic.

\begin{itemize}
\item \texttt{read} resolves a path relative to the workspace, rejects a resolved escape, and returns text or a directory listing. It does \emph{not} add line numbers, because a model might copy them into an exact-match patch.
\item \texttt{write} creates parent directories and calls \texttt{Path.write\_text}. The source does not implement a temporary-file-and-rename atomic-write protocol.
\item \texttt{patch} accepts a SEARCH/REPLACE block and requires exactly one occurrence of the search text in the current decoded file. It refuses missing or ambiguous matches and invalid UTF-8. Unique matching localizes the chosen replacement; it does not prove that the edit is correct, preserve all byte-level encodings, or eliminate concurrent-write races.
\item \texttt{shell} prompts for a complete command in interactive mode. Noninteractive execution requires both an allow switch and a matching tokenized command prefix; it executes an argument vector with \texttt{shell=False}. Interactive approval selects a different path using \texttt{shell=True}.
\end{itemize}

The file tools check workspace containment and protect top-level \texttt{.git} and \texttt{.nakedagent} targets. These are application checks, not an operating-system sandbox. Shell commands and arbitrary plugin code have separate authority, and filesystem races or host-specific aliases require separate evaluation.

\subsection{Fenced-text invocation}
A response is parsed into an \emph{ordered list} of tool calls. The grammar uses a column-zero triple-backtick opener, a tool name, optional arguments and a body. The parser is a line scanner with a stack of fence lengths, not a single regular-expression extraction. It normalizes CRLF, tracks nested fences and emits a reserved refusal call for an unclosed block. See \texttt{toolcall.py} and the foundation specification for exact rules.

\begin{lstlisting}
```patch src/calculator.py
<<<<<<< SEARCH
return a - b
=======
return a + b
>>>>>>> REPLACE
```
\end{lstlisting}

This avoids requiring a provider's native function-calling wire format; it still imposes a tool-call grammar on model text. Tagged examples at column zero can be interpreted as requests. No measured advantage over native tool calling, or general success rate for small models, follows from the grammar alone. The implementation acknowledges inspiration from gptme~\cite{gptme} and uses a search/replace convention comparable to Aider's documented edit formats~\cite{aiderformats}.

In the functional path, an admitted USER\_INPUT, MODEL\_REPLY, TOOL\_RESULT, ESCALATE, ALARM or TERMINATION consumes one event slot. Thus \texttt{max\_steps} is an event budget, not a model-token budget, wall-clock limit or number of successful tool executions. The default imperative loop counts rounds differently (Table~\ref{tab:paths}). Reporting only ``25 steps'' without naming the path is ambiguous.

At the final event slot the reducer becomes terminal and suppresses returned dispatch actions. For example, with a budget of two, USER\_INPUT followed by a MODEL\_REPLY containing a tool request consumes the budget and dispatches no tool. With three slots, one synthetic tool result can be admitted. A transition receipt can contain parsed proposed actions even when the terminal transition returns no executable actions. These distinctions are covered by the companion check.

The Sidekick gate's routes are ALLOW, BLOCK and ESCALATE. BLOCK adds an ALARM and terminates; ESCALATE records the held action and suspends unless the event budget is exhausted. A subsequent user event lifts suspension and the model re-decides. That is not a signed human authorization token or an atomic approval of the exact previous action. The default gate matches a short list of destructive strings and assigns fixed scores; it has no escalation band and supplies no calibrated risk probability. Broader gate policy is an extension point, not an established safety result.

The standard-library MCP client is a subprocess/stdio JSON-RPC implementation with a declared 2024-11-05 protocol version. It mounts external tools into Sidekick before the first event. Stdio is a transport, not a guarantee that the child process lacks network access. The protocol's transport specification~\cite{mcptransport} does not by itself establish implementation conformance or authority isolation.

\section{What offline replay establishes}
\subsection{Reducer and hash contract}
The core has Mealy-style form
\[
  \delta(S_i,E_{i+1})=(S_{i+1},A_{i+1}).
\]
It is a deterministic reducer over structured state, not a finite-state automaton in the strict sense: arbitrary text and metadata give an unbounded abstract state space, even with a bounded event count. The state contains a step counter and budget, message history, transition receipts, terminal status/reason, declared policy and suspension status. It does not contain a pending-action/result matching relation.

Let $J$ be the implementation's UTF-8 encoding of JSON with sorted keys, compact separators, ASCII escaping and nonfinite numbers disallowed. Let $H$ denote SHA-256, $P$ the system prompt, $B$ the event budget and $Q$ the declared policy. Genesis is
\begin{align*}
 G &= \{\text{system\_prompt}:P,\text{max\_steps}:B,\text{policy}:Q\},\\
 h_0 &= H(J(G)).
\end{align*}
For each admitted transition, the following \emph{named fields} are hashed:
\begin{lstlisting}
{
  "prev_hash": h_previous,
  "step_index": i,
  "event": {"event_type": kind,
            "payload": text,
            "metadata": metadata},
  "actions": [{"tool_name": name,
               "args": args,
               "content": content}, ...]
}
\end{lstlisting}
The receipt calls this digest \texttt{state\_hash}, but it is not a direct serialization of every state field. State is reconstructed by replay. This is a linear hash chain, rather than a branching Merkle tree with inclusion proofs. Nor is the Python serialization a claim of cross-language JSON canonicalization. Ports need separate hash-contract tests; the current foundation conformance specification explicitly excludes the functional/replay layer.

\subsection{Conditional consistency argument}
Fix the reducer/parser implementation, initial frame, and ordered event values. If their operations are deterministic on these values, repeated replay produces the same state and proposed actions, by induction on the event index: the initial state is fixed; equality of each predecessor state and event yields equality of the next state and receipt. This is an argument about the program's defined transition function. The companion examples are checks of particular cases, not a machine-checked proof of every implementation path.

The strict verifier parses the versioned header, contiguous event sequence and required final trailer; recomputes per-event hashes; compares them to the supplied hashes; and checks final status, reason, step count and hash. Post-terminal events and ignored suspended-state events are rejected. A successful log ends terminal or suspended. No provider, tool or plugin is executed during verification.

With a fixed trusted reference hash outside the attacker's control and suitable hash-security assumptions, modifying committed inputs should produce a mismatch. The stock verifier has no external reference-hash argument or authenticated recorder. It compares values supplied in the same local file. A writer able to change the file can generate a different valid event sequence and recompute its entire chain and trailer. It can also replace a run with another complete, internally valid run. The required trailer catches an incomplete ending, not all malicious history replacement.

\subsection{Threat model and counterexamples}
The relevant cases differ:
\begin{enumerate}
\item \textbf{Accidental or partial modification:} editing a payload while retaining its recorded hashes is rejected.
\item \textbf{Coherent replacement:} editing events and recomputing hashes can pass. There is no signature-based origin authentication, non-repudiation or independently witnessed history in the current log.
\item \textbf{False effect report:} a TOOL\_RESULT can be admitted without a prior matching tool request. The reducer records it as input, so replay alone does not establish dispatch causality or that the stated result is true.
\item \textbf{Different environment:} identical reported inputs replay identically even if the model identity, executed binary, files or external effects were misreported. The declared model/workspace fields are commitments to labels, not measurements of those resources.
\end{enumerate}

The companion \texttt{paper/check\_claims.py} exercises these distinctions. In particular, coherent replacement and an unrequested TOOL\_RESULT are \emph{expected acceptance} cases. Their acceptance limits the claim rather than demonstrating a failure of deterministic hashing. A transparency design with signed checkpoints, retained independent copies and consistency verification would add different guarantees; Certificate Transparency illustrates such additional machinery~\cite{rfc9162}. We do not claim that NakedAgent implements that protocol.

The event writer flushes records but does not establish immutable storage. A new log normally opens in write mode; resuming a suspended run replaces its final trailer before appending continuation events. ``Append-only'' describes ordinary event accumulation during a run, not an enforced storage property or crash-proof durability. Logs may contain prompts, source text and tool results; confidentiality and retention need deployment policy.

\section{Omakase: replace the opinion, retain the seam}
NakedAgent's Omakase doctrine offers four selected tools while allowing operators to substitute implementations without replacing the dispatcher. A Python plugin exports \texttt{TOOLS}, \texttt{DISABLE}, or both. Workspace-local plugins require explicit trust; user-global plugins are always considered. Later directories and files override earlier tools, after which disabled names are removed.

The useful coupling is between registry and prompt: a tool's optional \texttt{.usage} attribute contributes its example, and tools without that attribute are listed by name. Replacing a patch implementation and its usage text updates the advertised interface together. This reduces one source of prompt/dispatch disagreement; it does not check that the example correctly describes the function or that a model follows it.

Disabling \texttt{shell}, \texttt{write} and \texttt{patch} removes the three mutating \emph{foundation} tools. Disabling only shell and write leaves patch available. Neither configuration proves a whole process read-only: plugin imports execute arbitrary Python and may add effects under any tool name. Dependency minimalism and extension freedom therefore pull in different directions. A deployment must inventory its active tools, imported plugins and external programs separately from the foundation package.

\subsection{Interpretation}
The pilot preserves useful engineering hypotheses: provider capability mismatch can prevent a run; tool examples can be echoed literally; Windows text pipes can contaminate Linux patch bytes; and a localized patch can still fail semantic tests. These observations motivate controlled probes. They do not show that a smaller model's parameters caused the final failure or that minimal scaffolding removes all harness friction. Both the adapter and sampling conditions changed across configurations. In particular, mini-swe-agent used temperature zero while the NakedAgent report says the provider default was used; the numeric value of that default was not recorded.

Invalid C1/C2 outputs must be distinguished from valid unsuccessful attempts. The reported C3 zero of three is descriptive of this small selected case study, not an estimate of general SWE-bench performance. Absence of raw trajectories prevents reclassification of individual failures or verification of the seven-regression count here.

\subsection{Prospective evaluation}
A comparative study should freeze source and plugin hashes, model/quantization digest, provider version, prompts, decoding parameters, task selection, base commits, container images and scoring version. Repeat matched runs across preregistered task strata and report run-level variation. Keep invalid infrastructure attempts separate from valid attempts; disclose both and a predetermined rerun rule. Save request/response traces, exact patch bytes, exit status and complete grader output.

Separate outcomes should include parse acceptance, tool dispatch, patch applicability, target-test improvement, preserved regression tests, final resolution, latency and token/cost budgets. A useful ablation changes one of fenced-vs-native invocation, concrete-vs-placeholder examples, or file-tool-vs-shell editing while holding the other conditions fixed. The historical pilot cannot substitute for those comparisons.

\section{Security and engineering limitations}
Removing third-party Python runtime packages reduces one set of update and package-selection obligations. It does not eliminate vulnerabilities in the interpreter, TLS stack, executable search path, provider, plugins or project scripts. No dependency-count survey or measured risk reduction is claimed for competing agents. Nor does the existence of a small implementation establish production readiness.

The noninteractive shell boundary depends on direct argument-vector execution and the selected executable's semantics, not on tokenization alone. An allowed interpreter or program with execution-capable flags may exercise broad authority. Interactive shell syntax, Windows batch files and environment-dependent executable resolution require separate analysis. Workspace path checks are not a proof against all symlink races, mount changes or filesystem aliases.

Replay also has engineering limits. It verifies one pinned semantics against reported events, not that every event admitted by the reducer could be produced by the live driver. The current genesis does not automatically measure the provider endpoint, binary, plugin source, full shell policy or workspace snapshot. The immutable tuple-based trace/history construction also copies growing sequences; no asymptotic or empirical performance advantage is established. Bounded event counts do not bound individual model responses, file sizes or arbitrary tool costs.

The contribution remains useful within these limits: one can inspect the effect boundary, substitute a tool together with its prompt example, test the parser without a model and replay a recorded state trajectory without re-executing effects. Those are concrete mechanisms on which a larger evaluation or stronger recorder can build.

\section{Reproducibility and availability}
The source is linked at an exact commit~\cite{nakedagentsource}. The paper README maps each claim to source files, distinguishes frozen artifacts from the living manuscript, and gives build commands. The post-hoc notebook records which checks were actually run. The following checks require no model service:
\begin{lstlisting}
python paper/check_claims.py
python -m examples.replay_demo
python -m unittest discover -s tests
\end{lstlisting}
The first command verifies the pinned runtime source inventory and eight synthetic claim checks. The repository's broader tests include parser, path, budget, log, resume and transport cases; passing them is regression evidence, not exhaustive verification. Rebuilding this paper does not regenerate historical benchmark trajectories or a deposited PDF. A future release should archive the exact manuscript, code snapshot, check outputs and any newly collected experimental data together.
